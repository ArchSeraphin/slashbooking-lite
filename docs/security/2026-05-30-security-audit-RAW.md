## Findings détaillés (triés par sévérité)

### 1. [HIGH] Public booking rate limit trivially bypassed via spoofable client IP
*Fichier :* `src/Http/PublicBookingController.php` :217-231 (isRateLimited) · *confiance audit :* high · *statut :* ⏳ NON vérifié

**Problème.** The unauthenticated POST /slashbooking/v1/bookings endpoint (permission_callback => __return_true, no nonce) relies on isRateLimited() as its primary anti-automation control alongside Turnstile (which fails open when unconfigured, see SB-ABUSE-003). isRateLimited() keys the transient on REMOTE_ADDR; while REMOTE_ADDR itself is not spoofable over plain TCP, it IS the proxy/load-balancer IP on the many commercial hosts that sit behind a reverse proxy or CDN (Cloudflare, nginx, Varnish, k8s ingress). On such installs every visitor shares one or a few REMOTE_ADDR values, so a single attacker exhausts the global 5/min bucket but, more importantly, the plugin never reads the real per-client forwarding header here, and there is no global cap or backoff. Worse, when REMOTE_ADDR is empty (CLI/edge/misconfig) the method returns false and disables throttling entirely. Combined with the 5/window/IP ceiling being shared, an attacker on a unique source IP simply rotates source IPs (cheap from any botnet/cloud) to get a fresh bucket each time. There is no nonce on this public route, so nothing else stands between the attacker and unlimited booking creation.
**Exploit.** An unauthenticated attacker scripts POSTs to /wp-json/slashbooking/v1/bookings from rotating source IPs (or, on a CDN/proxy-fronted site, simply observes that everyone shares the proxy IP). Each distinct REMOTE_ADDR gets its own md5 transient bucket, so the 5/min ceiling is escaped, and on proxied sites the plugin throttles the proxy rather than the attacker. The attacker floods the bookings table and the admin mailbox (see SB-ABUSE-002) at high volume.
**Correctif.** Make the rate limit fail-closed when no usable IP is available. Add a global per-minute cap independent of IP so source-IP rotation cannot fully escape throttling. On proxied installs, resolve the true client IP from a trusted-proxy allowlist (configurable, off by default) rather than ignoring forwarding headers. Tighten the window and add exponential backoff. Most importantly, gate the public POST behind a server-issued single-use submission nonce that the widget bootstrap hands out, so blind scripted POSTs are rejected.

### 2. [HIGH] Plugin auto-update from GitHub performs no install-time integrity/authenticity verification (published .sha256 is never checked); GitHub-account or release-pipeline compromise = fleet-wide silent RCE
*Fichier :* `src/Updates/UpdateChecker.php` :17-51 · *confiance audit :* high · *statut :* ⏳ NON vérifié

**Problème.** The auto-update channel is yahnis-elsts/plugin-update-checker (PUC v5.6) pointed at a public GitHub repo. PUC (vendor/.../Vcs/GitHubApi.php getLatestRelease) takes whatever ZIP asset matches /slashbooking-.*\.zip$/i on the latest GitHub Release, sets it as downloadUrl, and hands it to WordPress's installer, which extracts it over the live plugin and executes it on the next request. Transport to api.github.com/github.com is HTTPS (GitHubApi.php:296,330 hardcode https://, so passive network MITM is mitigated), and release.yml even publishes a slashbooking-<v>.zip.sha256 sidecar (line 66) -- BUT nothing verifies it: PUC/WordPress never consume the .sha256, there is no upgrader_pre_download / upgrader_source_selection hook, no GPG/minisign/Sigstore signature check, and no per-release hash pin. Confirmed by grepping sha256/hash_file/signature/upgrader_pre_download/upgrader_source_selection across src/, slashbooking.php, bin/, .github/ (no matches). The trust model thus reduces to 'anyone who can publish a Release on github.com/ArchSeraphin/slashbooking can push arbitrary PHP to every customer site.' For a COMMERCIAL plugin sold to many sites this single GitHub identity is a high-value RCE pivot with no defence-in-depth; wp.org-hosted plugins at least pass through wp.org review/signing, which this self-hosted channel lacks.
**Exploit.** An attacker steals the maintainer's GitHub token/credential (phishing, leaked PAT, compromised dev machine) or gains push via a compromised CI Action (SUPPLY-003). They publish Release v1.0.25 with a malicious slashbooking-1.0.25.zip containing a web shell in src/Plugin.php. Within the PUC check window every customer site sees 'Update available'; admins click 'Update now' (or WP auto-updates), the trojaned ZIP is extracted and executed as the web-server user on every install -- mass RCE across the customer base, with no integrity check that could have blocked it.
**Correctif.** Verify the artifact before WordPress installs it. Minimum: hook 'upgrader_pre_download' (or PUC's puc_pre_inject_update) and reject unless the downloaded ZIP's SHA-256 matches a value obtained over an authenticated channel -- you already publish the .sha256, so fetch and enforce it (ideally pin the expected hash via the readme/Version metadata PUC already downloads). Better: sign each release ZIP (minisign/cosign/GPG) in release.yml and verify a detached signature with a public key shipped in the plugin before extraction. Combine with SUPPLY-003 (pin Actions, tighten token scope, require 2FA + tag protection on the publishing account). Document the update trust model for buyers.

### 3. [MEDIUM] OAuth callback uses a long-lived, replayable HMAC state token with no one-time/nonce binding to the initiating session
*Fichier :* `src/Http/AdminGoogleController.php` :118-166 (callback), 107-116 (start); src/Google/OAuthState.php:14-47 · *confiance audit :* medium · *statut :* ✅ confirmé

**Problème.** The Google OAuth callback /slashbooking/v1/admin/google/oauth/callback is public (permission_callback => '__return_true', AdminGoogleController.php:52) and is authorized solely by OAuthState::verify() on the `state` query parameter. The state token is a stateless HMAC over `oauth|{userId}|{exp}` with a 600s TTL (OAuthState.php:8,18). It is NOT stored server-side, NOT marked single-use, and NOT bound to the admin's session/cookie. Within the 10-minute window the same state token can be replayed any number of times, and the userId encoded in it is never actually consulted by callback() — the connected account is always saved as the single global account regardless of who initiated. Because the endpoint is public and the state is the only gate, an attacker who can obtain a valid state value (e.g. via Referer leakage to Google/3rd-party scripts on the OAuth screen, browser history, proxy logs, or by observing the redirect) can complete the exchange with an authorization code, or feed an attacker-controlled `code`, to write Google credentials into the site. This is effectively a login-CSRF / account-injection on the OAuth connection that a true CSRF nonce or one-time state would prevent.
**Exploit.** An admin clicks 'Connect Google' which calls /oauth/start and is redirected to Google with state=S (valid for 10 min). The attacker obtains S (Referer header sent to Google/analytics, shared screen, browser history on a shared machine, or a logged proxy). The attacker completes Google consent on their OWN Google account, captures the resulting `code`, then requests GET /slashbooking/v1/admin/google/oauth/callback?state=S&code=ATTACKER_CODE directly (no auth needed). exchangeCode() succeeds and the plugin stores the attacker's refresh/access tokens as the site's single Google account, so all bookings sync to the attacker's calendar (data exfiltration of customer PII: names, addresses, phones, appointment times) and the attacker can inject/delete calendar events that drive site availability.
**Correctif.** Make the OAuth state single-use and bound to the initiating session: store the issued state (or a random nonce) in a transient/user-meta keyed to the current user at /oauth/start, and in callback() require that the decoded userId equals an authenticated session OR that the stored single-use value matches and then delete it (replay protection). Prefer not to reuse sb_decision_secret for the OAuth HMAC. Additionally, since the callback only ever runs for a logged-in admin returning from Google, consider verifying current_user_can(Capabilities::MANAGE) in callback() and reject if the cookie session does not match the userId embedded in state. Implement PKCE to bind the code exchange to the original request.
**Vérification.** CONFIRMED REAL after reading the cited files and the full call path.

EVIDENCE (all read directly):
1. Callback route is public and reachable. src/Http/AdminGoogleController.php:49-53 registers GET /admin/google/oauth/callback with permission_callback => '__return_true'. RestRouter wires AdminGoogleController under namespace Plugin::REST_NAMESPACE = 'slashbooking/v1' (src/Plugin.php:11; src/Http/RestRouter.php:171-179), so GET /wp-json/slashbooking/v1/admin/google/oauth/callback is callable by any unauthenticated visitor. (Note: the unblockPublicEndpoints whitelist in RestRouter does NOT even list this route, but it doesn't need to — the permission_callback is already __return_true.)

2. Authorization is solely OAuthState::verify($state). src/Http/AdminGoogleController.php:118-125: callback() reads code and state from query params and the only gate is `$this->state->verify($state) === null`. No current_user_can, no nonce, no cookie/session check.

3. State is a stateless, replayable HMAC with no single-use/session binding. src/Google/OAuthState.php: issue() (14-21) builds base64("oauth|{userId}|{exp}|{hmac}") with TTL_SECONDS=600 (line 8). verify() (23-47) only checks base64 decode, 4-part shape, ctype_digit, expiry (exp < now), and hash_equals on the HMAC. It is not stored server-side, not flagged single-use, not bound to a cookie. The same token is replayable unlimited times within the 10-minute window.

4. The userId embedded in state is never consulted for the connection. verify() returns (int)$userIdStr (line 46), but callback() discards the return value beyond the `=== null` null-check (line 123). The connected account is saved as the SINGLE global account regardless of who initiated: callback() uses $this->accounts->findSingle() (line 141) and $this->accounts->save($account) (line 162) — no per-user keying. So the "account-injection" variant is real: an attacker who obtains a live state can submit their OWN authorization code (GET /callback?state=S&code=ATTACKER_CODE); exchangeCode() (src/Google/OAuthClient.php:48-57) exchanges whatever code is supplied, and the resulting refresh/access tokens become the site's global Google account.

5. Secret reuse confirmed: src/Http/RestRouter.php:151 constructs new OAuthState((string) get_option('sb_decision_secret')) — the very same secret used by DecisionTokenSigner (RestRouter.php:129; Plugin.php:148), generated once at activation (src/Activator.php:93-95).

IMPACT: After token injection, customer bookings sync to the attacker's calendar (PII exfiltration: names, addresses, phones, appointment times — confirmed sync path exists in Plugin.php ~line 205+), and attacker-controlled calendar events drive site availability (busy-block pull). Legitimate, embarrassing flaw for a paid product.

ADVERSARIAL / HONEST LIMITS (why medium, not high):
- The attacker CANNOT forge state: it is HMAC'd with a server-only secret, and /oauth/start requires Capabilities::MANAGE (AdminGoogleController.php:44-48,102-105,107-112) plus a logged-in user (start() returns 401 if userId===0). A low-priv/unauth user cannot mint a fresh state.
- Therefore the attack REQUIRES capturing a legitimate admin's live, unexpired (<10 min) state. The report's strongest leak vectors are realistic but not trivial: browser history on a shared admin machine, proxy/SIEM/access logs capturing the redirect URL with state, shoulder-surf/screen-share. The "Referer to third-party scripts on the OAuth consent page" vector is weak (the consent page is Google's own origin and Google legitimately holds the state). This token-capture prerequisite is exactly why severity is medium rather than high.

MINOR INACCURACY in the original report: it states verify() yields the userId that callback consults; verify() does return the userId, but callback() ignores it. This reinforces rather than weakens the finding ("userId never consulted").

FIX CONFIRMED ABSENT: no transient/user-meta single-use store, no PKCE (authUrl in OAuthClient.php:30-43 sends no code_challenge), no session/cookie binding, no capability check in callback(). All of the report's recommendations remain unimplemented.

VERDICT: Real and exploitable in practice given the (non-trivial but realistic) prerequisite of capturing a live state token. Adjusted severity: medium (confirmed).

### 4. [MEDIUM] Public OAuth callback (__return_true) implants Google Calendar credentials with no logged-in/capability check and no CSRF binding to the initiating admin
*Fichier :* `src/Http/AdminGoogleController.php` :49-53, 118-166 · *confiance audit :* high · *statut :* ✅ confirmé

**Problème.** The route /slashbooking/v1/admin/google/oauth/callback is registered with permission_callback => '__return_true' (line 52) and is reachable by any unauthenticated internet visitor. The only gate in callback() (line 123) is $this->state->verify($state). OAuthState::verify (src/Google/OAuthState.php:23-47) only proves the state token was HMAC-signed by this site and is unexpired; it returns the embedded userId, but callback() discards that value (only checks `=== null`). It never calls current_user_can(Capabilities::MANAGE) and never confirms the current request comes from the admin who initiated the flow. The state token is handed to the admin's browser in the JSON of /oauth/start (line 115) and then round-trips through Google as a query parameter, so it is not a session-bound secret. Once any party presents a still-valid state token (600s TTL) plus an OAuth `code`, callback() exchanges the code (line 128) and overwrites the site's single GoogleAccount row (findSingle/save lines 141-162) with the resulting refresh/access tokens. The token implantation happens before the 302 redirect to admin_url(...), independent of any admin session.
**Exploit.** OAuth account-injection / login-CSRF calendar takeover. An attacker who controls a Google OAuth client registered with this site's redirect URI (or who captures a still-valid state token from an admin via referrer/history/screen-share) crafts a GET callback URL containing a valid state value and an authorization `code` for an attacker-controlled Google account, and hits it directly (the route is __return_true GET, no login needed). The plugin silently connects calendar sync to the attacker's Google account: thereafter the site pushes all customer bookings (name, email, phone, address PII) into the attacker's calendar and pulls the attacker's events as busy-blocks, corrupting availability. No admin authentication is required at the moment the callback fires.
**Correctif.** After state verification, require current_user_can(Capabilities::MANAGE) (return 403 otherwise) and bind the flow to the initiating user by comparing the userId returned from OAuthState::verify() to get_current_user_id(). Make the state single-use: store an issued nonce in user-meta/transient at /oauth/start and consume it in the callback. Enforce all of this before exchangeCode().
**Vérification.** VERIFIED REAL but the original severity/framing is partly overstated. I read the three load-bearing files in full.

CONFIRMED defects:
1. src/Http/AdminGoogleController.php:49-53 — /admin/google/oauth/callback is registered with permission_callback => '__return_true', methods GET, reachable without authentication.
2. AdminGoogleController.php:118-166 — callback() only gates on `$code === '' || $this->state->verify($state) === null`. The userId returned by verify() is discarded; there is NO current_user_can(Capabilities::MANAGE) and NO comparison of the verified userId against get_current_user_id(). After verification it unconditionally calls exchangeCode($code) (line 128) and overwrites the single GoogleAccount row via findSingle()/save() (lines 141-162), persisting whatever refresh/access tokens result. No mitigation present.
3. src/Google/OAuthState.php:23-47 — verify() only proves the state token is HMAC-signed by this site and unexpired (600s TTL). It is NOT single-use: no nonce stored/consumed, so a captured state is replayable for 600s. Returns userId, ignored by caller.

ADVERSARIAL CORRECTIONS to the finding:
- The auditor's primary exploit ("an attacker who controls a Google OAuth client registered with this site's redirect URI") is WRONG. src/Google/OAuthClient.php:48-57 exchangeCode() uses THIS site's client_id + client_secret + fixed redirectUri. Google binds an authorization code to the client_id/redirect_uri that issued it, so a code minted under an attacker's separate OAuth client cannot be redeemed against the victim's confidential client. That variant does not work.
- The "any unauthenticated internet visitor, no preconditions" framing is overstated. To complete the flow the attacker needs a VALID, unexpired (<=600s) `state` token. The only way to MINT one is /oauth/start, which IS capability-gated (canManage, line 47) and HMAC-signed with a server secret. An unauthenticated attacker cannot forge or mint state.

THE REAL EXPLOIT (login-CSRF / OAuth code-injection): An attacker runs the victim site's own legitimate OAuth consent flow against the attacker's own Google account (the consent URL/client_id/redirect_uri all belong to the victim and the public consent page is reachable), obtaining a valid `code` for the attacker's Google account. If the attacker then obtains any live victim-issued `state` token within the 600s window (referrer leakage from the OAuth-completion admin page to a third party, browser history on a shared/kiosk machine, screen-share, or replay since state is not single-use) and hits the callback with that state + the attacker's code, the site silently stores the ATTACKER's refresh token. Thereafter customer PII (name/email/phone/address) is pushed to the attacker's calendar and attacker events are pulled as busy-blocks, corrupting availability. This is a genuine account-injection / calendar-takeover and the missing capability check + missing user-binding + replayable state are all real, fixable defects.

SEVERITY: downgraded high->medium because the exploit requires capturing a live state token (capability-gated to mint) — it is not the no-precondition unauthenticated takeover the writeup implies — but it is a legitimate CSRF-class flaw worth fixing in a commercial product.

FIX (correct as written): after state verification, require current_user_can(Capabilities::MANAGE) (403 otherwise) AND compare the userId returned by OAuthState::verify() to get_current_user_id(); make state single-use by storing an issued nonce in user-meta/transient at /oauth/start and consuming it in callback; enforce all of this before exchangeCode().

### 5. [MEDIUM] Token encryption key auto-stored in the same database (wp_options) as the encrypted tokens, defeating encryption-at-rest against a DB dump
*Fichier :* `src/Google/EncryptionKeyResolver.php` :30-32 (random key generated and written to wp_options 'sb_enc_key' when no constant is defined) · *confiance audit :* high · *statut :* ⏳ NON vérifié

**Problème.** EncryptionKeyResolver::resolve() first tries the SLASHBOOKING_ENC_KEY constant (lines 14-20), then a hex key in wp_options('sb_enc_key') (lines 22-28); if neither exists it auto-generates a 32-byte key and persists it hex-encoded in wp_options under 'sb_enc_key' (lines 30-31). On a default install no constant is defined, so the DB-fallback is the normal path. The libsodium-secretbox-encrypted Google access/refresh tokens (GoogleAccountRepository toRow() columns oauth_access_token_enc / oauth_refresh_token_enc, lines 63-64) live in the SAME database, as do sb_google_client_secret, sb_decision_secret, and watch_token_secret. Therefore a single database dump (SQLi in any other plugin, leaked/readable backup, shared-host snapshot, or compromised DB credentials) yields both the ciphertext and its key, so the otherwise-correct encryption (Encryption.php, libsodium secretbox with random nonce + authenticated decryption -- cryptographically sound) provides no confidentiality against the most common WordPress compromise vector. MITIGATING FACTOR: Plugin.php:396-403 does show an admin_notice when usingFallback() is true, telling the admin to define SLASHBOOKING_ENC_KEY in wp-config.php -- but only to users with manage_options, it is dismissible-by-ignoring, and the plugin still functions (and stores the key in the DB) if ignored.
**Exploit.** An attacker obtains a copy of the database (SQLi elsewhere, exposed backup, host snapshot). They read sb_enc_key from wp_options, hex-decode it, and sodium_crypto_secretbox_open the oauth_refresh_token_enc value to recover the long-lived Google refresh token, plus the plaintext sb_google_client_id/sb_google_client_secret. They mint Google access tokens at will and read/modify the connected calendar (all customer booking PII) indefinitely without touching the WordPress site again.
**Correctif.** Prefer a key outside the DB by default: on first run attempt to write define('SLASHBOOKING_ENC_KEY', ...) into wp-config.php (as core does for salts), or escalate the existing admin notice (make it non-trivially dismissible / block connecting until set). Document in the commercial product that tokens are 'protected at rest only when SLASHBOOKING_ENC_KEY is set in wp-config.php'.

### 6. [MEDIUM] Editor role granted full management capability (slashbooking_manage), including Google OAuth credentials and all customer PII
*Fichier :* `src/Admin/Capabilities.php` :16 (GRANTED_ROLES = ['administrator', 'editor']); 26-39 (install() adds MANAGE+VIEW to both); 47-55 (syncOnUpgrade re-applies on every boot via Plugin.php:96) · *confiance audit :* high · *statut :* ⏳ NON vérifié

**Problème.** Capabilities::GRANTED_ROLES is ['administrator', 'editor'] (line 16) and install() grants slashbooking_manage to both (lines 28-38). syncOnUpgrade() (lines 47-55, called every boot from Plugin.php:96) ensures editors get the cap even on upgrade. Every privileged Google route gates on current_user_can(Capabilities::MANAGE): /admin/google/settings read returns client_id + redirect_uri and write sets client_id/client_secret (AdminGoogleSettingsController.php:15,21,26), /admin/google/oauth/start, /admin/google/disconnect, /admin/google/diagnostics, plus /admin/bookings (all customer PII). In standard WordPress an editor is a content manager not expected to administer third-party OAuth integrations or view all customer personal data. The code comment (lines 12-15) justifies this for the original single-tenant SMB usage, but for a COMMERCIAL plugin shipped to many sites it broadens the privilege-escalation/insider-threat surface: a compromised editor (lower bar than admin) can reconfigure Google client credentials, disconnect/reconnect the calendar (chaining with SB-OAUTH-01), and export all booking PII.
**Exploit.** A site grants the editor role to a freelance content writer (typical). The account is phished or its password reused/leaked. The attacker logs into wp-admin as the editor, opens SlashBooking Google settings, overwrites client_id/client_secret with attacker-controlled values (or just reads all bookings via /admin/bookings), then initiates an OAuth connect to an attacker Google project -- hijacking calendar sync and exfiltrating all customer names/emails/phones/addresses. No administrator action required.
**Correctif.** Default GRANTED_ROLES to ['administrator'] only. If delegated booking management is needed, make it filterable (e.g. apply_filters('slashbooking_manage_roles', ['administrator'])) so operators opt in, and consider splitting capabilities so managing OAuth credentials requires administrator while merely viewing/handling bookings can use the lesser slashbooking_view cap.

### 7. [MEDIUM] Email bombing / notification amplification via unauthenticated booking creation
*Fichier :* `src/Booking/CreateBooking.php` :63-67 (do_action booking_created) -> src/Notifications/BookingNotifier.php:33-42 (onCreated) · *confiance audit :* high · *statut :* ⏳ NON vérifié

**Problème.** Every successful public booking fires slashbooking/booking_created, which BookingNotifier::onCreated handles by sending one email to the visitor-supplied customer_email AND one to the business inbox. The recipient of the first email is fully attacker-controlled (the booking 'customer_email', validated only as a syntactically valid address in CreateBooking::validate). There is no per-recipient throttle and no nonce; the only gates are the bypassable IP rate limit (SB-ABUSE-001) and Turnstile (fail-open when unconfigured, SB-ABUSE-003). This turns the booking endpoint into an email amplifier: an attacker chooses the recipient and mails an arbitrary third party from the victim site's trusted sending domain/SMTP, while simultaneously flooding the business inbox. Because email is dispatched synchronously inside the request (wp_mail), it is also a DoS amplification vector (each cheap HTTP request fans out to remote SMTP work, and the request also writes a temp ICS file on confirm flows).
**Exploit.** Combined with SB-ABUSE-001, an attacker submits valid-looking bookings with customer_email=victim@target.com at volume. The site sends a 'booking received' email to victim@target.com on each request, mail-bombing the victim from the site's domain and damaging the domain's sender reputation, while also flooding the admin inbox and bloating the bookings table.
**Correctif.** Add a per-recipient-email and a global send-rate cap that is independent of IP. Move notification dispatch off the request path to an async queue (Action Scheduler / wp_schedule_single_event). Require an effective anti-automation check (mandatory Turnstile or server-issued single-use nonce) before sending any customer-facing confirmation. Cap bookings per email per day.

### 8. [MEDIUM] Turnstile CAPTCHA fails open when secret key is empty (default install has no bot protection)
*Fichier :* `src/PublicFront/TurnstileVerifier.php` :41-45 (verify) and 36-39 (isConfigured); gated at PublicBookingController.php:159 · *confiance audit :* high · *statut :* ⏳ NON vérifié

**Problème.** TurnstileVerifier::isConfigured() is false whenever sb_turnstile_secret_key is empty, and createBooking() only enforces the CAPTCHA when isConfigured() is true. Out of the box sb_turnstile_secret_key is unset, and an admin can clear it (AdminSettingsController write supports the __CLEAR__ sentinel) with no warning. In that default/common posture the only remaining anti-automation on the public booking POST is the honeypot field and the bypassable IP rate limit (SB-ABUSE-001) - effectively no real bot protection for a paid product. The fail-open design means the most security-sensitive public endpoint ships unprotected by default.
**Exploit.** A site owner installs SlashBooking and never sets up Cloudflare Turnstile (typical). Every public booking request passes the CAPTCHA gate unconditionally, enabling the spam/DoS/email-bombing in SB-ABUSE-001/002 with no attacker effort and no admin awareness.
**Correctif.** Treat 'no CAPTCHA configured' as fail-secure for this internet-facing endpoint: when Turnstile is unconfigured, fall back to a mandatory server-issued single-use submission nonce plus strict rate limiting instead of accepting all requests. Surface a prominent, persistent admin notice when no CAPTCHA secret is set so the owner knows the booking form is unprotected.

### 9. [MEDIUM] Release & CI workflows pin third-party GitHub Actions to mutable tags and grant workflow-wide contents:write, widening the build supply-chain that feeds the unverified update channel
*Fichier :* `.github/workflows/release.yml` :8-60 · *confiance audit :* high · *statut :* ⏳ NON vérifié

**Problème.** Every third-party Action in release.yml and ci.yml is referenced by a mutable major-version tag (@v4, @v2) rather than a pinned 40-char commit SHA. Mutable tags can be silently retargeted by the action's maintainer or an attacker who compromises that action's repo (the ecosystem has seen this, e.g. tj-actions/changed-files). These actions run inside the release job that holds workflow-level `permissions: contents: write` and produces the ZIP that auto-deploys to all customers -- chained with SUPPLY-001 (no install-time verification), a poisoned build step yields fleet-wide RCE. softprops/action-gh-release and shivammathur/setup-php are popular targets. The contents:write grant is scoped to the whole workflow rather than only the publish step, and no GitHub Environment / required-reviewer gate protects the release.
**Exploit.** An attacker compromises (or the maintainer of) shivammathur/setup-php, softprops/action-gh-release, or actions/setup-node retargets its @v2/@v4 tag to a backdoored revision. The next time a v* tag is pushed, the release job (running with contents:write) executes the malicious step during npm run build or the gh-release upload and ships a trojaned slashbooking-<v>.zip. Because the update channel performs no signature/hash verification (SUPPLY-001), the backdoor auto-propagates to every customer on next update.
**Correctif.** Pin every `uses:` to a full commit SHA (e.g. softprops/action-gh-release@<40charsha> # v2.x) and let Dependabot bump them. Remove the workflow-level `permissions: contents: write`; grant write only to the publish step via a step/job-scoped token, and gate the publish behind a GitHub Environment with required reviewers. Adopt OIDC + keyless Sigstore signing of the ZIP in the same job so the artifact is independently verifiable (feeds SUPPLY-001).

### 10. [MEDIUM] Raw exception message rendered into the public 1-click decision page
*Fichier :* `src/Http/DecisionController.php` :75-80 · *confiance audit :* high · *statut :* ⏳ NON vérifié

**Problème.** The /slashbooking/v1/decide endpoint is public (permission_callback __return_true), protected only by an HMAC decision token. ### 43. [FALSE-POSITIVE] OAuth state token reuses the decision/email signing secret (key reuse across two HMAC schemes)
*Fichier :* `src/Http/RestRouter.php` :129, 151; src/Google/OAuthState.php:10-19; src/Booking/DecisionTokenSigner.php:8-17 · *confiance audit :* high · *statut :* ❌ faux positif

**Problème.** Both the booking decision/cancel token signer and the OAuth state signer are constructed with the SAME secret, get_option('sb_decision_secret') (RestRouter.php:129 for DecisionTokenSigner, RestRouter.php:151 for OAuthState). They sign different message formats ('decide|..|..|exp' / 'cancel|uid|exp' vs 'oauth|userId|exp'), so cross-protocol forgery is not directly possible today because the message prefixes differ, but sharing one key across two independently-designed token systems is fragile: any future change to a payload format, or a parsing ambiguity, could allow a signature minted for one purpose to validate for another. It also means a single secret compromise breaks both customer-facing booking links AND the OAuth connection trust simultaneously, and rotating one forces rotating the other.
**Exploit.** Defense-in-depth concern rather than a direct exploit: if a later refactor makes the OAuth and decision payload namespaces overlap (e.g. both becoming pipe-delimited integers without a distinct, fixed domain-separation prefix), an attacker holding a legitimately-issued decision token could repurpose its HMAC as a valid OAuth state, or vice-versa, bypassing the intended authorization boundary.
**Correctif.** Use separate, independently-generated secrets for the two HMAC schemes (e.g. sb_decision_secret and a new sb_oauth_state_secret), or derive per-purpose subkeys via HKDF/hash_hmac(secret, 'oauth-state') and hash_hmac(secret, 'decision'). Keep a fixed domain-separation prefix in every signed message (already partially present).
**Vérification.** Adversarial verification of sb-csrf-002 (OAuth state token reuses the decision/email signing secret).

Files cited: src/Http/RestRouter.php:129,151; src/Google/OAuthState.php:10-19; src/Booking/DecisionTokenSigner.php:8-17. Both signers are constructed with get_option('sb_decision_secret') — key reuse is real. The question for an exploit is whether key reuse enables cross-protocol signature forgery or any boundary bypass.

It does not, by the finding's own admission. Domain separation via fixed message prefixes (decide / cancel / oauth) means HMAC-over-full-message yields disjoint valid signature sets per scheme. No attacker-usable confusion exists in the current code. The exploit scenario is explicitly framed as conditional on a future refactor that removes domain separation — i.e., it audits hypothetical code, not shipped code. Per the audit rules (prefer fewer high-confidence findings, honest severity, refute speculation, default to skepticism), this is a false positive as a vulnerability; at most it is info-level key-hygiene advice (derive per-purpose subkeys via hash_hmac(secret,'oauth-state') / hash_hmac(secret,'decision'), or use a separate sb_oauth_state_secret).

Confidence is tempered by an environment limitation: all tool outputs returned empty in this session, so I could not re-read the files to byte-verify the message formats or confirm constant-time comparison in verification. The refutation rests on the formats quoted in the finding and the auditor's own statement that the prefixes differ; those are internally consistent, so the verdict stands, but the file contents were not independently re-confirmed.
**Raison faux positif.** The finding describes a hypothetical, not an exploitable vulnerability in the shipped code. The auditor's own description concedes "cross-protocol forgery is not directly possible today because the message prefixes differ," and the exploit_scenario is explicitly conditional: "if a later refactor makes the OAuth and decision payload namespaces overlap." Auditing shipped code, a flaw that exists only after a hypothetical future refactor is not a real finding.

Cryptographic reasoning on the quoted formats: HMAC is computed over the ENTIRE message. The three message types carry distinct fixed leading domain-separation tokens (decide|.., cancel|.., oauth|userId|exp). A signature produced over an oauth|... message can never validate against a verifier that recomputes the MAC over a decide|.. / cancel|.. reconstruction, and vice versa — the recomputed digests differ for any differing input. So there is no authorization-boundary bypass and no signature-reuse path today. An attacker without the secret cannot mint a valid token of EITHER scheme regardless of key sharing.

The two residual points are weak: (1) "single secret compromise breaks both schemes" — true but a non-issue, because a secret compromise already fully breaks each scheme independently; sharing the key does not give an attacker any leverage they don't already have once the key is known. (2) "future refactor could remove domain separation" — speculative about code that does not exist. The HKDF / per-purpose-subkey recommendation is reasonable hygiene worth a one-line hardening note, but it is not a real or exploitable security flaw and should not ship as a vulnerability finding in a commercial audit.

CAVEAT: A harness failure in this session returned empty output for every tool call (Bash echo/cat/sed/find/base64 and the Read tool alike), so I could not independently re-read the source to byte-confirm the exact message formats or that constant-time hash_equals() is used in verification. My refutation relies on the message formats quoted in the finding plus the auditor's own admission that the prefixes differ. If those quoted formats are accurate (and they are self-consistent with the file:line citations), the false-positive conclusion holds.
